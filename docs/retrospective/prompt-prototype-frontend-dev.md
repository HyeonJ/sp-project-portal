# 개선 프롬프트 — 프로토타입 기반 프론트 개발

> `frontend-fidelity-drift.md` 회고의 액션 아이템 #1. 다음에 프로토타입을 baseline으로 프론트를 개발시킬 때, "baseline"이라는 단어 하나에 의존하지 않도록 **충실도·방법·DoD·충돌 우선순위**를 박은 시작 프롬프트.

## 0. 의도된 충실도 수준 (이번에 누락됐던 것)

| 수준 | 의미 | 선택 |
|------|------|------|
| **A. 1:1 마크업** | 프로토타입의 실제 마크업·클래스·인터랙션을 그대로 옮김. screen-design은 보조 명세 | ✅ **채택** |
| B. 시각 동일 | 보이는 결과만 동일하면 마크업 구조는 자유 | — |
| C. UX 동일 | 동작 흐름만 같으면 시각/마크업 차이 허용 | — |

> 근거: 사용자가 반복 요구한 "프로토타입의 퍼블이랑 똑같이 보이게", "프로토타입 그대로 가져와". **다른 수준을 원하면 위 표에서 바꾸고 아래 프롬프트의 해당 문장을 수정할 것.**

---

## 1. 복붙용 시작 프롬프트

```
[프론트 개발 — 프로토타입 baseline]

기준 산출물:
- 퍼블/마크업/인터랙션의 단일 진실 원천(SoT) = docs/prototype/index.html
- 명세 보조 = docs/screen-design/, docs/api-spec.md, docs/requirements.md

충실도 수준: 1:1 마크업.
- 각 화면은 프로토타입의 실제 마크업·클래스·인터랙션을 "옮긴다". 화면설계서를 보고 새로 그리지 않는다.
- SSR화에 필요한 변형(Thymeleaf fragment 분리, 서버 데이터 바인딩, CSRF)만 가하고, 그 외 DOM 구조·클래스명·모달 흐름·confirm·드롭다운·드롭존·미리보기·건수 표시·empty state는 프로토타입과 동일하게 유지한다.

충돌 우선순위:
- 프로토타입 ↔ screen-design/api-spec이 어긋나면 → UI/인터랙션은 프로토타입이 이긴다.
- 어긋남을 발견하면 임의로 한쪽을 따르지 말고 먼저 보고한다(어느 문서를 갱신할지 결정 후 진행).

작업 방법:
1. 시작 전 docs/prototype/index.html의 화면 목록을 추출해 [프로토타입 화면 → SSR 템플릿] 매핑 표를 만든다.
2. 화면 단위로 진행한다. 한 화면 = (프로토타입 마크업 이식) + (서버 바인딩) + (충실도 비교 통과).
3. 화면마다 완료 직전, 프로토타입 화면과 SSR 렌더를 나란히 비교해 아래 DoD를 통과시킨다.

완료 기준(DoD) — 화면별:
- [ ] gradlew build 그린 (컴파일+테스트)
- [ ] 프로토타입과 시각 비교: 레이아웃·간격·타이포·색 동일
- [ ] 인터랙션 비교: 모달 open/close, 스타일드 confirm, 드롭다운, 드롭존, 미리보기/건수, 정렬, empty/로딩/에러 상태 모두 프로토타입과 동일하게 동작
- [ ] 프로토타입에만 있고 SSR에 빠진 요소 0개 (체크 후 명시)
- [ ] 자동화 브라우저로 검증 시: 파일 선택창 등 네이티브 다이얼로그는 CDP가 막으므로 "안 열림"을 버그로 단정하지 말 것

진행 추적:
- 매핑 표에 화면별 충실도 상태(미착수/이식됨/비교통과)를 기록하고, "비교통과"가 아닌 화면은 완료로 보고하지 않는다.
```

## 2. 왜 이 4종이 들어갔나 (회고 매핑)

| 프롬프트 요소 | 막으려는 드리프트 | 회고 근거 |
|---------------|-------------------|-----------|
| **SoT = 프로토타입** 명시 | 화면설계서 기준으로 재구현되며 마크업 0% 포팅 | 원인 4-2 |
| **방법 = "옮긴다, 새로 그리지 않는다"** | "디자인 토큰만 이식"으로 좁혀진 집행 | 원인 4-1 |
| **충돌 우선순위** | 프로토타입 vs 화면설계서 모순 시 임의 선택 | 원인 4-2 |
| **화면별 DoD에 비교 통과** | 완료 기준이 build green뿐, 충실도 게이트 부재 | 원인 4-3 |

## 3. 재사용 템플릿 — "선언된 baseline은 게이트로 강제하라"

프로토타입뿐 아니라 **모든 baseline/동결 산출물**에 적용되는 일반 원칙(회고 액션 #2):

```
[baseline 강제 체크 — 모든 "기준/동결" 산출물에]

1. 이 baseline의 SoT는 무엇인가? (문서 / 코드 / 프로토타입 중 하나로 단일화)
2. baseline과 구현의 일치를 "사람 약속"이 아니라 "장치"로 강제하는가?
   - 퍼블 → 화면별 시각/동작 비교 게이트
   - API → springdoc 코드 생성 또는 contract test
   - 스키마 → 마이그레이션 + 정합 테스트
3. 강제 장치가 없으면 baseline을 "동결"이라 부르지 않는다 (썩는 스냅샷일 뿐).
4. 어긋남 발견 시 그 자리에서 "왜"를 한 줄 남긴다 → silent drift가 아니라 추적 가능한 결정으로.
```

> 참고: 이번 MVP의 api-spec도 "v1.0 동결 baseline"을 선언했으나 springdoc 미연결로 코드가 드리프트했다(회고 원인 4-4). 같은 처방이 적용된다.
