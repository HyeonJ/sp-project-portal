# 개선 프롬프트 — api-spec 기반 백엔드 개발

> `api-spec-divergence-inventory.md` 개선안의 실행. 다음에 api-spec을 두고 백엔드를 구현시킬 때, "기준 문서 중 하나"로 흘려보내지 않도록 **스펙의 권위 수준·정합 장치·스코프컷 반영·분기 기록**을 박은 시작 프롬프트.

## 0. 먼저 정할 것 — 스펙의 권위 수준 (이번에 누락됐던 것)

| 모드 | 의미 | 강제 장치 | 언제 |
|------|------|-----------|------|
| **코드-우선** | 수기 스펙은 설계 스케치(비권위). 코드가 SoT | **springdoc** 연결 → 스펙 자동 생성 | MVP·속도 우선 ✅ (이번 프로젝트 권장) |
| **스펙-우선(계약)** | api-spec이 구속력 있는 계약 | **contract test**(경로·메서드·스키마 검증) | 안정 API·외부 소비자 |

> 이번 MVP는 api-spec 스스로 "런타임 SoT=springdoc"이라 적었으므로 **코드-우선**이 일관된다. 단, springdoc을 실제로 연결해야 "코드-우선"이 성립한다(이번엔 안 붙여서 수기 스펙이 유일 계약이 돼버림).

---

## 1. 복붙용 시작 프롬프트 (코드-우선 모드)

```
[백엔드 개발 — api-spec 기반]

스펙의 권위: 코드-우선.
- docs/api-spec.md는 설계 스케치다(구속력 있는 계약 아님). 런타임 SoT는 코드.
- 단, 그러려면 springdoc-openapi를 연결해 /v3/api-docs·Swagger UI가 코드에서 생성되게 한다. 이게 "코드-우선"의 전제다.

구현 원칙:
- 엔드포인트는 데이터모델·트랜잭션에서 자연스러운 형태로 설계하되, 스펙과 달라지면 "왜"를 한 줄 남긴다(예: "vno path 제거 — 서버가 현재 버전 판별").
- 스펙에 있는데 이번에 안 만드는 기능(스코프 컷)은 같은 커밋에서 api-spec에 🔲 미구현(범위 외)로 표기한다. 스펙이 거짓말하지 않게.

정합 게이트(Phase/PR DoD):
- [ ] gradlew build 그린 (컴파일+테스트)
- [ ] springdoc 생성 문서와 수기 스펙의 엔드포인트 목록 diff → 불일치는 (스펙 갱신) 또는 (코드 수정)으로 같은 PR에서 해소
- [ ] 스코프 컷 항목은 스펙에 🔲 표기됐는지 확인
- [ ] 인가 매트릭스(admin/team/client/member/non-member) 테스트 통과

진행 추적:
- 스펙 섹션별로 [구현/미구현/분기(사유)] 상태표를 유지한다. "분기"는 사유 없이 두지 않는다.
```

> 스펙-우선(계약) 모드면 위 "코드-우선" 문장을 "api-spec이 계약이며, 경로·메서드·요청/응답 스키마를 contract test로 강제한다. 코드가 스펙과 다르면 빌드 실패"로 교체하고, DoD의 diff 항목을 contract test 통과로 바꾼다.

## 2. 왜 이 요소들이 들어갔나 (회고 매핑)

| 프롬프트 요소 | 막으려는 드리프트 | 회고 원인 |
|---------------|-------------------|-----------|
| **스펙 권위 수준 명시 + springdoc 전제** | "기준 6개 중 하나"로 흘려보냄 / drift 방지 장치 미연결 | R1·R3 |
| **스코프 컷을 같은 커밋에 스펙 반영** | Phase C "시간 허용 시" 컷이 스펙에 미반영(미구현 9건) | R2 |
| **분기 시 "왜" 한 줄** | 더 나은 설계로의 분기가 silent drift로 남음 | R1 |
| **DoD에 스펙 diff / contract test** | 완료 기준이 build green뿐, 정합 게이트 부재 | R4 |

## 3. 공통 원칙

`prompt-prototype-frontend-dev.md` §3 "선언된 baseline은 게이트로 강제하라"와 동일한 처방의 백엔드 적용판이다. 프론트=화면별 눈 비교, 백엔드=springdoc/contract test. **둘 다 "선언"이 아니라 "장치"다.**
