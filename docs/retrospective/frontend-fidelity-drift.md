## 1. 한 줄 요약

프로토타입 HTML을 프론트 baseline으로 지시했으나, 빌드 계획서가 프로토타입의 역할을 **"디자인 토큰 이식"으로 좁히고** 화면은 화면설계서 기준으로 **재구현**하면서, 39개 화면의 퍼블이 프로토타입에서 광범위하게 어긋났다. **충실도 검증 게이트가 없어** 사용자가 매 드리프트를 사람 눈으로 잡아냈다.

## 3. 무슨 일이 있었나

화면을 프로토타입에서 옮긴 게 아니라 화면설계서를 보고 새로 그렸기 때문에, 화면마다 프로토타입과 어긋났다. 사용자가 발견·지적한 드리프트(부분 목록):

1. 스타일드 삭제 confirm 증발 → 즉시 삭제됨
2. CSV 가져오기: 모달·드롭존·미리보기·건수 통째로 사라지고 다른 동작
3. TC 등록·결함 등록 모달이 프로토타입과 다르게 보임
4. 결함 등록 시 연관 TC 연결 로직 누락
5. 헤더 프로젝트 드롭다운 미동작
6. 대시보드 최근활동 길이 (5건 제한 필요)
7. 커스텀 select chevron / 드롭다운 스타일

> 이것들은 개별 버그가 아니라 **"프로토타입과 다르다"는 같은 종류의 드리프트가 반복**된 것이며, confirm·모달·드롭다운·레이아웃·인터랙션 전반에 걸쳐 있었다. 특정 두 섹션에 국한되지 않음.

## 5. 잘된 점

- walking-skeleton-first는 통합 리스크(세션·CSRF·MyBatis·Flyway·Testcontainers)를 일찍 노출한 좋은 전략 — 유지할 것
- 매 Phase `gradlew build` 그린 규율은 일관되게 지켜짐
- 디자인 토큰 이식(OKLCH·사이드바·컴포넌트)은 시각적 일관성의 바닥은 잡아줌 — 색·폰트 단위 드리프트는 거의 없었음

## 6. 교훈 / 액션 아이템

1. **시작 프롬프트에 4종을 명시한다**: 충실도 수준 · 방법(포팅 vs 재구현) · DoD(화면별 비교 통과) · 충돌 우선순위. → `prompt-prototype-frontend-dev.md`
2. **baseline은 선언이 아니라 게이트로 강제한다.** 퍼블=프로토타입 옆에 띄워 눈 비교, API=codegen(springdoc) 또는 contract test. 강제 장치 없는 "동결"은 사회적 약속일 뿐.
3. **지시→계획 번역 시 핵심 명사의 의미 보존을 확인한다.** "baseline"이 계획서에서 무엇으로 구체화됐는지 사용자가 한 번 검수.
4. **완벽한 프롬프트도 검증 루프 없이는 드리프트를 못 막는다.** 39화면 재구현이면 프롬프트가 1:1이라 적혀도 사람이 안 보면 어긋남 → 프롬프트 + DoD 비교, 둘 다 필요.
